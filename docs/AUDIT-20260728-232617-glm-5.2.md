## Dimensão 1 — Precedência de intenção (latest-user-wins)

**O que o código faz hoje.** O prompt de saída é montado em `buildOutboundPrompt` (`src/ui/outboundPrompt.ts:177`). A ordem per-message é: `[pendingTasksSummary] → [guardrails] → SHELL_EXECUTION_PREAMBLE → EXECUTION_CONTINUITY_PREAMBLE → [policy/role once] → [tracking once] → [checkpoint once] → [resumeCheckpoint] → [interruptedBy] → [sessionId] → [autonomy] → [rtk] → [todo] → [bootstrap] → [seed] → [handoff]`, tudo prependido ao user text com separadores `\n\n---\n\n`. Para backends role-aware viram mensagens `developer` separadas; CLIs colam no user text (`outboundPrompt.ts:287-290`).

Em `OpenAISession.send` (`session.ts:384-440`) a ordem pushada para `this.messages` é: gap-closer assistant opcional, depois **preamble developer messages** (413-418), depois **a user message** (423). User text é a última — posição de cauda de maior atenção. Correto.

Os reminders são *explicitamente subordinados*: `pendingTasksSummary` (`controllerHubState.ts:81-89`), `todosSummary` (`todos.ts:254-264`), e o prefixo de compactação carregam o contrato "LATEST USER MESSAGE is the source of truth / YIELD to redirects".

### DEFECT 1.1 — "stop" / "only document" não invalida trabalho futuro enfileirado incompatível
1. **DEFECT:** Não há mecanismo host-level que registre uma diretiva de cancelamento/redirect e a aplique a turnos posteriores. Precedência de intenção é enforcement *só por prompt wording*, repetido per-message. Uma mensagem enfileirada antes do "stop" não é reavaliada quando de fato despacha.
2. **EVIDENCE:** `src/ui/chatController.ts:234-264` (`onSend`). Turno busy + `mode === "send"` (default) enfileira (`this.queue.enqueue(msg)`). O item enfileirado despacha depois com preamble re-lido, mas a única coisa que poderia neutralizar o request anterior é o reminder text dizendo para ceder. Não há comparação do novo user text contra intents enfileirados, nem marcador "o usuário disse stop no turno N" carregado adiante.
3. **IMPACT:** Usuário envia "refatorar o módulo auth" (enfileirado enquanto busy). Enquanto roda, usuário envia steer "stop, só escreve um doc". O steer cancela o turno e despacha imediatamente (bom). Mas o item enfileirado "refatorar auth" ainda está na queue e despacha depois do turno do doc terminar (`chatController.ts:402-408`), re-armado o trabalho de refatoração que o usuário acabou de mandar parar — o reminder per-message é a única coisa que pode parar, e LLMs rotineiramente ignoram phrasing soft "yield to the latest user message" quando uma tarefa concreta enfileirada está na frente.
4. **FIX:** Quando um steer/redirect carregando sinal claro de cancelamento chega, limpar (ou marcar superseded) a queue existente por default; ou persistir um "active intent/cancel directive" per-session que o dispatcher consulta antes de enviar uma mensagem enfileirada.
5. **RISK:** Medium (UX: mudar semântica de queue pode surpreender usuários que dependem de FIFO).
6. **VALUE:** High.

### DEFECT 1.2 — `followupAnchor` carrega objective stale como mensagem developer de cauda de alta autoridade
1. **DEFECT:** `OpenAISession.followupAnchor` (`session.ts:271-285`) apende, na *cauda* de todo request windowed (maior atenção), uma mensagem `developer`/`system` "OBJECTIVE: ... GUIDANCE: every tool call must move the OBJECTIVE forward". O `objective` é setado só de user text ≥8 chars que não é interjeição "continue/ok/sim" (`session.ts:424-428`). Um redirect como "stop, just verify" é ≥8 chars e não está na lista, então *sobrescreve* `objective` — essa parte está bem. Mas o anchor **nunca é limpo em semântica de cancelamento/redirect**, e no split CLIs-vs-API essa cauda developer-role pode outranquear a última user message real para modelos que ponderam developer acima de user.
2. **EVIDENCE:** `session.ts:271-285` (role é developer/system, colocada na cauda via `turnRunner.ts:181-185` `anchor ? [...windowed, anchor] : windowed`).
3. **IMPACT:** Quando a última mensagem do usuário é correção estreita ("just run the tests now"), o anchor ainda instrui "every tool call must move the OBJECTIVE forward" apontando para o objective broad anterior, puxando o modelo de volta para a tarefa antiga. Compete diretamente com o contrato latest-user-wins.
4. **FIX:** Tratar o objective como derivado/secundário: quando a última user message é curta ou é redirect, omitir ou downgrade o anchor; ou nunca usar role `developer` para o anchor (usar context note claramente rotulada), e dizer explicitamente "yields to the latest user message".
5. **RISK:** Low–Medium.
6. **VALUE:** Medium.

**Robusto aqui:** a ordenação central (preamble → user, user em tail position) está correta; os reminders são explicitamente self-demeaning; guardrails estão corretamente rotulados highest-priority e re-enviados todo turno (`outboundPrompt.ts:210-216`).

## Dimensão 2 — Estado vs intenção (work-items separados de checkpoints)

**O que o código faz hoje.** Dois task types: `task-anchor` (trabalho executável) e `task-checkpoint` (estado observado), definidos em `src/sync/tasks.ts:30-38`. O split é enforcement *por filtro*:
- `fetchSessionTasks` (`tasks.ts:112`) retorna AMBOS — para display (`list_tasks`, painel).
- `fetchPendingWorkItems` (`tasks.ts:147`) retorna só `task-anchor && !done` — o caminho de intenção.
- `fetchSessionCheckpoints` (`tasks.ts:158`) retorna só checkpoints.
- `fetchLatestCheckpoint` (`tasks.ts:207`) retorna só checkpoint real **sem fallback para task-anchor**.

O reminder do prompt usa `fetchPendingWorkItems` (`controllerHubState.ts:51-57`), então checkpoints nunca chegam à linha "CURRENT task". O next-step hand-back do `task_complete` usa `fetchPendingWorkItems` também (`run.ts:256`). Separação limpa e correta.

### DEFECT 2.1 — `setTaskDone` defaulta registro typeless para `task-anchor`, mas checkpoint typeless seria reclassificado silenciosamente (latente, não atualmente triggerável)
1. **DEFECT:** Em `setTaskDone` (`tasks.ts:164-187`), `const type = obs?.type || TASK_ANCHOR;` defaulta registro sem `type` para `task-anchor`. O comentário justifica como "completar trabalho nunca deve reclassificar em tipo historical-fact". É o default certo para o path de complete — mas é a *única* guarda. Se um checkpoint perde seu `type` (hub data migration, partial save, hand-restored record), completá-lo reclassifica em `task-anchor` e apareceria em pending work — exceto que completion também adiciona `DONE_TAG`, então é filtrado. Efeito líquido hoje: benigno.
2. **EVIDENCE:** `src/sync/tasks.ts:182-184`.
3. **IMPACT:** Low/latente — nenhum path atual produz checkpoint typeless; o DONE_TAG mascara a reclassificação. Notado como smell de corretude, não bug ativo.
4. **FIX:** Nada requerido agora; se registro typeless for possível, preservar `task-checkpoint` quando o histórico/tags indicarem que era checkpoint.
5. **RISK:** Low.
6. **VALUE:** Low.

### DEFECT 2.2 — `memory_save` de `type: "task*"` é session-scoped, mas o type string é model-controlled e não validado contra os dois valores permitidos
1. **DEFECT:** Em `run.ts:106-124` (`memory_save`), o agente fornece `type` livremente; `sessionScoped = ctx.sessionId && type.startsWith("task")` (`run.ts:114`). Qualquer `task-foobar` é aceito e session-scoped. `fetchSessionTasks`'s `isTask` matches `String(type).startsWith("task")` (`tasks.ts:34`), então um `task-foobar` bogoso aparece no painel e `list_tasks`, mas `isWorkItem`/`isCheckpoint` retornam false, então é invisível ao caminho de intenção. Só suja o display sem papel executável ou resume.
2. **EVIDENCE:** `src/adapters/aiTools/run.ts:109,114`; `src/sync/tasks.ts:34-38`.
3. **IMPACT:** Agente confuso emitindo `type:"task-note"` polui o painel Tasks com itens que não são nem work nem checkpoint e nunca podem ser limpos por `task_complete` (não são `task-anchor`).
4. **FIX:** Validar `type` contra `{ "task-anchor", "task-checkpoint" }` para o path session-scoped; rejeitar ou normalizar `task-*` desconhecidos em `memory_save`.
5. **RISK:** Low.
6. **VALUE:** Low–Medium.

**Robusto aqui:** Esta dimensão é a mais forte no codebase. O split anchor/checkpoint é consistentemente enforcement em todo read site, a ghost window de search-index-lag (`tasks.ts:53-67`), o cascade sequential-batch para numbered plans (`tasks.ts:78-98`, `run.ts:226-244`), e a recusa de auto-completar user-requested tasks no cascade (`run.ts:231-238`) são todos bem-considerados.

## Dimensão 3 — Compactação de contexto (summary não-executável)

**O que o código faz hoje.** O compactor (`src/adapters/openai/compactor.ts`) é incomumente bem-hardened:
- `SUMMARY_PREFIX` + `SUMMARY_BODY_INTRO` (`compactor.ts:22-29`) declaram o block "REFERENCE ONLY ... NOT an instruction and NOT a plan", e enumeram explicitamente reverse signals (stop, undo, only document) que cancelam trabalho histórico.
- `renormalizeSummary` (`compactor.ts:70-89`) rewrites headings imperativos proibidos (`Immediate next actions`, `Remaining work`, `Next steps`, `Resume exactly`, `Active task`) em históricos, stripa resume lines imperativos, e defanga code fences executáveis (`sh/bash/python/...`) em pointers `[ran: ...]`.
- A summarize instruction (`compactor.ts:221-239`) proíbe imperativos e prescreve um set fixo de headings históricos.
- A última user message real é preservada no tail verbatim (`compactor.ts:186-189`); se o tail não tem user msg, a última é unshifted.
- Summaries anteriores são re-folded, não stacked, tolerantes ao prefixo legacy `[Summary so far` (`compactor.ts:164-168`).

### DEFECT 3.1 — O summary é uma mensagem `developer` (alta autoridade) apesar de declarado reference-only
1. **DEFECT:** O summary sintético usa `role = supportsDeveloperRole ? "developer" : "system"` (`compactor.ts:190-194`). Para providers OpenAI-compatible, `developer` é o role de *maior autoridade* (acima de user). O summary é rotulado "REFERENCE ONLY" no texto, mas seu role channel diz o oposto ao modelo: isto é instrução autoritativa. O contrato de texto e o role channel se contradizem.
2. **EVIDENCE:** `src/adapters/openai/compactor.ts:190-194`.
3. **IMPACT:** Em providers que ponderam fortemente developer messages, um imperativo que sobrevive renormalization (phrasing não em `FORBIDDEN_HEADINGS`/`IMPERATIVE_RESUME_LINES`, ex: "You were implementing X" que lê como continuation directive) é entregue com autoridade máxima, minando o contrato "latest user message is the only source of the active task".
4. **FIX:** Usar canal de baixa autoridade para o summary: uma mensagem `system` colocada na região prefix (não no canal developer), ou um "context recap" user-role que não pode outranquear a última user message real. O texto reference-only é necessário mas não suficiente; o role deve concordar.
5. **RISK:** Medium (mudar role pode afetar providers que handle system vs developer diferente; precisa teste per-backend).
6. **VALUE:** Medium–High.

### DEFECT 3.2 — Renormalization é regex-anchored e facilmente evadida
1. **DEFECT:** `FORBIDDEN_HEADINGS` matches strings de heading exatas (`compactor.ts:39-45`) e `IMPERATIVE_RESUME_LINES` matches um set fixo de verbos leading (`compactor.ts:53`). Um imperativo semanticamente equivalente que não match o regex passa verbatim: "## Things still to do", "### Your job now", "Next, finish the tests", "The remaining step is to deploy".
2. **EVIDENCE:** `src/adapters/openai/compactor.ts:39-53`.
3. **IMPACT:** O hardening é bypassável por paraphrase. Combinado com 3.1 (developer role), um summary criativamente mild do modelo pode smuggle um directive ativo em context de alta autoridade.
4. **FIX:** Ou (a) drop a reliance em imperative-filtering inteiramente e em vez disso fazer o summary role low-authority (fixa 3.1, de-risks 3.2), ou (b) broaden detection (block-list plus positive allow-list: só os 7 headings prescritos permitidos; rewrite/strip qualquer outro).
5. **RISK:** Medium.
6. **VALUE:** Medium.

**Robusto aqui:** Apesar de 3.1/3.2, isto é engenharia genuinamente forte. O contrato reference-only, re-fold idempotente com tolerância legacy, preservação de last-user-message, defanging de executable-fence, e fail-safe (qualquer erro deixa context intocado, `compactor.ts:173-176`) são todos corretos e claramente reasoning. `history.ts` reconstrói corretamente o transcript lossless do ledger para display.

## Dimensão 4 — Identidade de turno, idempotência e retomada

**O que o código faz hoje.** Identidade estável é implementada cuidadosamente:
- `logicalTurnId = sessionId/turn-<seq>` (`turnId.ts:32`), com `seq` persistido para `meta.json.nextTurnSeq` (`session.ts:346-352`) e reconstruído no resume de meta ou ledger fallback (`session.ts:99-108`).
- `attemptId = logicalTurnId/attempt-<n>` per model POST (`turnId.ts:40`, assigned em `turnRunner.ts:245`).
- Retry reusa o logicalTurnId original: `retryLastMessage` passa `retryOf = from.lastTurnId` (`surfaceBranching.ts:99`), que flui para `send(..., resumeTurnId)`, staged como `pendingResumeTurnId`, consumido por `resumeTurn()` (`session.ts:362-372`).
- Dedup: `MessageDedup.accept` (`controllerQueue.ts:156-167`) dropa repeats do mesmo `clientMessageId`; mensagens sem id bypassam dedup (retry/edit-resend legítimos).

### DEFECT 4.1 (HIGH) — Um Retry duplica a user message em history
1. **DEFECT:** `OpenAISession.send` **incondicionalmente** pusha uma nova user message e apende uma user ledger row, independentemente de `resumeTurnId` (retry) estar setado. Não há branch que detecte "isto é retry do mesmo turno" e skip re-push do user text. O dedup gate não ajuda porque retries não carregam `clientMessageId` (composer path) — `retryLastMessage` chama `handleMessage({type:"send", ...})` sem um (`surfaceBranching.ts:100`), então `MessageDedup.accept` retorna true (bypassed).
2. **EVIDENCE:** `src/adapters/openai/session.ts:419-437` — o user `push` (423) e ledger `appendMessage` (429) rodam em todo `send`, sem guard `resumeTurnId`-conditional. Contraste `src/ui/chatController.ts:335` `if (!msg.interruptedBy) { this.emit({type:"user",...}) }` que suprime corretamente a bubble *rendered* para retry mas o host NÃO suprime a mensagem que de fato chega ao modelo.
3. **IMPACT:** User message: "Fix the bug in parser.ts". Turn falha com timeout. Usuário clica Retry. Agora `this.messages` contém o user text *duas vezes* (e duas user ledger rows), então o modelo vê `user("Fix the bug...") → assistant("(previous turn interrupted)") → developer(preamble) → user("Fix the bug...")` de novo. A UI visível mostra uma bubble (bom), mas o modelo e o ledger lossless agora têm um duplicate, que (a) desperdiça context, (b) num loop de multi-retry compõe, e (c) quebra o invariant lossless-ledger para qualquer replay/recovery. O retry é "attributable to the original turn" para observabilidade (logicalTurnId reused) mas o conteúdo conversacional é duplicado.
4. **FIX:** Em `send`, quando `resumeTurnId` é provido AND o turno falho deixou uma dangling unanswered user message que é textualmente idêntica a `text`, skip o novo user `push` + ledger append (reusar o existente); só pushar o gap-closer assistant se role alternation ainda precisar. Alternativamente, no path de retry, dropar o dangling user/assistant filler pair e resumir do pre-turn state.
5. **RISK:** Medium (deve handle os edge cases de role-alternation que o gap-closer atualmente cobre; precisa teste cuidadoso across providers).
6. **VALUE:** High.

### DEFECT 4.2 — Dedup set cresce unbounded pelo session lifetime
1. **DEFECT:** `MessageDedup.seen` (`controllerQueue.ts:157`) é um `Set<string>` sem eviction. O comentário claim que "is bounded by user-driven message count" — verdade per session, mas um host multi-session long-lived (o extension process) que segura muitos controllers, ou uma única sessão muito longa, acumula todo accepted id para sempre.
2. **EVIDENCE:** `src/ui/controllerQueue.ts:156-167`.
3. **IMPACT:** Memory leak, severidade low (ids são strings curtas; counts realistas são modestos). O dedup controller é per-`ChatController`, então é freed no controller disposal, que bound na prática. Notado como smell.
4. **FIX:** Cap com LRU/bounded set (ex: keep last N thousand), ou clear no session dispose (já efetivamente acontece já que o controller o possui). Opcional.
5. **RISK:** Low.
6. **VALUE:** Low.

### DEFECT 4.3 — `resumeTurn` aceita qualquer string contendo `/turn-` como logicalTurnId válido
1. **DEFECT:** `if (typeof id === "string" && id.includes("/turn-"))` (`session.ts:367`) é a única validação. Um id malformed/foreign (ex: string que a webview injetou via `retryOf`) é adotado como o current logicalTurnId, persistido em ledger rows, e usado em commit subjects. Não há check de que o id de fato pertence a *esta* sessão ou matches o formato `<sessionId>/turn-<n>`.
2. **EVIDENCE:** `src/adapters/openai/session.ts:362-372`.
3. **IMPACT:** Low na prática (o único caller é `retryLastMessage` lendo `from.lastTurnId`, que o adapter setou). Mas o surface contract é untrusted (webview-supplied `retryOf` flui através de `controllerMessageHandler.ts:22`), então uma mensagem crafted poderia hijackear o logicalTurnId namespace para observabilidade/ledger rows.
4. **FIX:** Validar `id.startsWith(sessionId + "/turn-")` e parsear o seq; fallback para `bumpTurn()` caso contrário.
5. **RISK:** Low.
6. **VALUE:** Low–Medium.

**Robusto aqui:** A reconstruction de monotonic-seq com meta + ledger fallback (`session.ts:99-108`), o orphan-recovery path que mantém requested id quando store file falta (`session.ts:76-87`), attemptId per hop (`turnRunner.ts:245`), e o controller capturando `lastLogicalTurnId` de `turn-start` (`chatController.ts:391-393`) são todos corretos e bem-traced. Dedup para o caso de transport double-delivery (mesmo `clientMessageId`) é sound.

## Dimensão 5 — Correção durante execução (redirect/steer/queue/stop)

**O que o código faz hoje.** Quatro send modes (`controllerQueue.ts:1`): `send`, `queue`, `steer`, `redirect`. O default enquanto busy é **`redirect`** (`package.json:938`). `onSend` (`chatController.ts:234-264`) branches:
- `redirect` + busy → `unshift` (front of queue, mantém queue existente), `cancel()`, emit queue. (246-251)
- `steer` + busy → `clear()` queue, `push`, `cancel()`. (252-256)
- qualquer outro + busy → `enqueue` (FIFO). (258-262)
- idle → dispatch.

Keyboard shortcuts (`composer.ts:254-266`): plain Enter = default selecionado; Shift+Enter = redirect; Ctrl/Cmd+Enter = steer; Alt+Enter = queue. O dropdown expõe redirect/queue/steer (`composer.ts:28`).

Design sound e bem-diferenciado.

### DEFECT 5.1 — `redirect`/`steer` cancelam o running turn mas não podem parar uma in-flight tool que já começou operação mutating
1. **DEFECT:** `cancel()` → `runner.cancel()` → `this.abort?.abort()` (`turnRunner.ts:99-101`). O abort signal aborta o in-flight HTTP fetch. Mas para uma *local tool já executando* (ex: `shell` command mid-run, ou `write_file` mid-write), o abort é best-effort: `runShell` recebe `abortSignal` (`shell.ts:56-59`) mas `write_file`/`edit_file` em `localRun.ts:214-277` **não** consultam `ctx.abortSignal` de forma alguma — uma vez entrado, o filesystem write roda até completion.
2. **EVIDENCE:** `src/adapters/aiTools/localRun.ts:214-227` (write_file) e `227-277` (edit_file) nunca referenciam `ctx.abortSignal`; só `shell` (`localRun.ts:169`) passa adiante.
3. **IMPACT:** Usuário envia steer "stop, don't write that" enquanto um `write_file` tool call acabou de ser dispatched no tool loop. O HTTP request aborta, mas o file write que já começou completa, mutando o workspace depois do usuário dizer stop. O próximo turno roda a correção steer, mas o unwanted write já aconteceu.
4. **FIX:** Checar `ctx.abortSignal?.aborted` no topo de `write_file`/`edit_file` (e antes do `writeFileSync` final), retornando resultado "interrupted" se aborted. Também await o abort entre tool dispatch e o write.
5. **RISK:** Low–Medium.
6. **VALUE:** Medium–High.

### DEFECT 5.2 — `steer` destroye a queue silenciosamente; `redirect` é default, mas plain `send` enquanto busy ainda enfileira (sem modo "stop")
1. **DEFECT:** Não há send mode "stop"/"cancel-only" explícito no enum (`controllerQueue.ts:1`). Um usuário que quer dizer "stop o que você está fazendo e não continue" deve ou clicar Stop (que cancela mas não carrega mensagem) ou usar steer/redirect (que ambos *enviam nova mensagem*). E `steer` limpa a queue inteira (`chatController.ts:253`) — incluindo future work legitimamente enfileirado que o usuário ainda quer — sem confirmação e sem recovery dos itens cleared.
2. **EVIDENCE:** `src/ui/chatController.ts:252-256` (steer clears queue); `controllerQueue.ts:1` (no stop mode); o Stop button posta `{type:"cancel"}` (`composer.ts:166`) que só cancela, sem mensagem.
3. **IMPACT:** (a) Usuário steerando com "wait, also remember X" perde seu backlog enfileirado inteiro. (b) Usuário que quer tanto stop E dar razão não pode fazer numa ação; o stop é message-less. A pergunta da dimensão "must 'stop' wait behind the current turn?" — não há stop *message* de forma alguma.
4. **FIX:** Considerar um `stop` mode (cancel + reason opcional, sem nova intent), e fazer o queue-clear do steer ou opt-in ou recoverable (ex: mover cleared items para uma lista "dismissed" que o usuário pode restaurar). No mínimo, documentar que steer limpa a queue no tooltip (`status.ts:25` diz "Interrupt the running turn and send now" mas omite "and clears the queue").
5. **RISK:** Low (additive).
6. **VALUE:** Medium.

### DEFECT 5.3 — Depois que redirect cancela o running turn, o turn-end handler auto-dispatcha o *front* queued item, que é o próprio redirect — mas ordering vs. failed turn é assimétrico
1. **DEFECT:** Isto é de fato handled cuidadosamente: um failed turn (`turnHadError`) NÃO auto-drains (`chatController.ts:402`), e `redirect` faz `unshift` então a correção roda next. Porém, o cancel do redirect causa um `turn-end`; o turn-end handler então `queue.shift()`s e dispatcha. Se o usuário emitiu redirect e *depois* uma segunda mensagem foi para a queue (FIFO) antes do cancel completar, o ordering é: redirect (unshifted para front) roda next, depois o FIFO item. Isto está correto. **O gap real:** não há guarda de que o cancel do redirect de fato parou tool execution antes do seu turn-end disparar o próximo dispatch — ver 5.1. Um write_file still-running do turno cancelado pode racear o dispatch do redirect.
2. **EVIDENCE:** `src/ui/chatController.ts:246-251` (redirect), `394-409` (turn-end auto-dispatch), combinado com `localRun.ts` write_file ignorando abort (5.1).
3. **IMPACT:** O redirect despacha e pode ele mesmo chamar write_file enquanto o write_file do turno anterior ainda está terminando — um filesystem race nos mesmos arquivos.
4. **FIX:** Mesmo que 5.1 (honrar abort em write/edit); adicionalmente, await tool quiescence antes de emitir turn-end para um turno cancelado.
5. **RISK:** Medium.
6. **VALUE:** Medium.

**Robusto aqui:** O model four-mode é bem-designed; `redirect` (cancel + keep queue + front-insert) é genuinamente um bom default que a maioria dos agentes erra. O failed-turn no-auto-drain gate (`chatController.ts:294, 402`) e o catch-block "don't auto-send on dispatch-setup failure" (`chatController.ts:347-358`) são ambos corretos e previnem failed turn de mascarar como continuation normal.

## Dimensão 6 — Guardrail de escopo e autorização (write-roots, commit scope)

**O que o código faz hoje.** Write containment host-level existe (`src/adapters/aiTools/writeRootGuard.ts`):
- `isPathInAllowedRoots` (`writeRootGuard.ts:23-30`) faz boundary check propre (`t === r || t.startsWith(r + path.sep)`) — sem prefix bug. Roots vazios/indefinidos → bypass (default unrestricted).
- `writeRootError` (`writeRootGuard.ts:36-42`) retorna string de guardrail quando out-of-root.
- `write_file` checa (`localRun.ts:221`), `edit_file` checa (`localRun.ts:230`), e `shell` checa seu `cwd` (`localRun.ts:151`).
- Roots são computados de `vscode.workspace.workspaceFolders` em `surfaceDialogues.ts:283-288` e fluem `SessionStartOptions.allowedWriteRoots` → `ToolContext.allowedWriteRoots` (`turnTools.ts:45`).
- Permission tiers (`permissionTiers.ts`): read/write/destructive, com `shell` classificado destructive (gated mesmo em manager mode). Plan mode hard-blocks writes (só novo `*.md` permitido, `localRun.ts:217`).
- O ledger comita em repo git *isolado* per-session (`ledger.ts:122-144`) com sua própria identity, `core.hooksPath /dev/null`, `commit.gpgsign false` — nunca o repo do usuário.

### DEFECT 6.1 (HIGH) — Shell containment checa só `cwd`, não o command content; arbitrary cross-repo writes via o próprio comando são desbloqueados
1. **DEFECT:** `shell` valida `args.cwd` contra as roots (`localRun.ts:147-152`) mas faz **zero** inspeção de `args.command`. Um comando como `git commit -am x` roda fine num cwd allowed, mas também `echo pwned > /etc/passwd`, `rm -rf ~`, `git -C /other/repo commit ...`, `cat > /home/user/.ssh/authorized_keys`, ou `curl ... | sh`. O goal stated do guardrail — "preventing the agent from writing across repo boundaries or into files outside the authorized workspace" — é derrotado por qualquer comando que escreve via redirection, `tee`, `cp`, `mv`, `git -C`, absolute paths, ou subshell.
2. **EVIDENCE:** `src/adapters/aiTools/localRun.ts:143-186` (shell branch): só `cwd` é checado; `command` é passado verbatim para `runShell`/`runShellInTerminal`. `writeRootGuard.ts` é path-based only.
3. **IMPACT:** O write containment host-level é efetivamente advisory para a tool mais poderosa. Um agente (ou instrução prompt-injected) pode trivialmente escapar: `shell({command: "echo bad > /etc/hosts", cwd: "<allowed>"})` passa o guardrail. Isto faz o write-root guardrail inteiro dar falsa assurance — as file tools são contidas, mas a shell tool é um escape hatch.
4. **FIX:** True containment de um shell arbitrary não é solúvel por string inspection. Opções: (a) rodar o shell dentro de um sandbox/seccomp/landlock/network-namespace OS-level confinado às roots (o único fix real); (b) se sandbox está out of scope, downgrade o claim — documentar claramente que `allowedWriteRoots` contém só as file tools e que `shell` é unconstrained, e gate `shell` atrás de approval (já é `destructive`, mas em `admin` mode roda free); (c) no mínimo, quando `allowedWriteRoots` está setado, requerer approval para todo `shell` independentemente de permission mode.
5. **RISK:** High (sandbox propre é mudança grande; a opção honesta-documentation é Low risk mas reduz o valor do feature).
6. **VALUE:** High.

### DEFECT 6.2 — Não há containment host-level para bridged VS Code Language Model tools (`runInTerminal`/`runTask`/`runTests`)
1. **DEFECT:** `runInTerminal`, `runTask`, `runTests`, e browser LM tools são classificados (`classifyLmTool`, `permissionTiers.ts:45-47`) mas `invokeLmTool` (`turnTools.ts:36`) é chamado com **nenhum** `allowedWriteRoots`/`cwd` context — só `args.name` e `args.input`. Estas tools rodam VS Code commands que operam em qualquer folder workspace que VS Code tem aberto, sem containment aplicado.
2. **EVIDENCE:** `src/adapters/openai/turnTools.ts:36` `if (isLmTool(args.name)) { return invokeLmTool(args.name, args.input); }` — bypassa a `ToolContext` construction inteiramente; `allowedWriteRoots` nunca é consultado para LM tools.
3. **IMPACT:** Quando `symposium.lmTools` está enabled, o agente pode rodar VS Code tasks/terminals arbitrary que tocam qualquer folder aberto, circumventando o write-root guardrail que bounda as native file/shell tools.
4. **FIX:** Ou excluir terminal/exec LM tools quando `allowedWriteRoots` está setado, ou routear seus cwd/targets pelo mesmo path de containment (e approval) que `shell`.
5. **RISK:** Medium.
6. **VALUE:** Medium.

### DEFECT 6.3 — `allowedWriteRoots` é silenciosamente vazio quando nenhum workspace folder está aberto (nenhum containment de forma alguma)
1. **DEFECT:** `surfaceDialogues.ts:283-288`: roots são setados só `if (folders.length)`. Com zero workspace folders (ex: single-file aberto, ou remote sem root), `allowedWriteRoots` fica undefined → `isPathInAllowedRoots` retorna `true` para todo path (`writeRootGuard.ts:24`) → **nenhum containment**. A sessão roda fully unrestricted sem warning ao usuário.
2. **EVIDENCE:** `src/ui/surfaceDialogues.ts:283-288`; `src/adapters/aiTools/writeRootGuard.ts:23-24`.
3. **IMPACT:** Usuário que abre o agent sem workspace folder (ou num scenario multi-root onde esperava containment) pega um agent unrestricted sem signal. O guardrail é opt-in-by-workspace-presence, não fail-closed.
4. **FIX:** Quando containment é o default pretendido, fail closed: se nenhum workspace folder, ou block write tools ou surface um notice claro ("no workspace root — writes are unrestricted"). No mínimo, emitir status notice para o usuário saber.
5. **RISK:** Low.
6. **VALUE:** Medium.

### DEFECT 6.4 — `git commit` via shell pode capturar pre-existing staged files (sem scope check no commit)
1. **DEFECT:** Não há host-level guard ao redor de `git commit` especificamente. Um agente rodando `git commit -am` ou `git commit` (com index pre-existing) dentro de cwd allowed vai commitar **o que estiver staged**, incluindo files que o usuário stagedou manualmente antes da sessão e files que o agente nunca tocou. O ledger usa `git add -A` no seu *próprio repo isolado* (`ledger.ts:227`) — isso é fine — mas os commits do agent shell-driven no *repo do usuário* são unchecked.
2. **EVIDENCE:** Nenhum code path inspeciona ou scopes `git commit` no user workspace. `src/scm/commitMessage.ts` é um command "generate commit message" user-triggered separado que só preenche o input box (nunca comita). O único path agent para commitar é `shell({command: "git commit ..."})`, que é subject só ao cwd check (6.1).
3. **IMPACT:** Usuário tem 3 files já staged para review cuidadosa. Agente, trabalhando numa task unrelated, decide "commit my changes" e roda `git commit -m "fix"` — capturando todos os 3 pre-staged files no commit do agente, possivelmente com a message do agente, antes do usuário revisá-los.
4. **FIX:** Quando um shell command match `git commit`/`git -C ... commit`, requerer approval (já é tier `destructive` para `shell`, mas só prompta em modes manager/user — em `admin` roda free). Considerar parsear staged-vs-agent-touched e warning. No mínimo, documentar claramente.
5. **RISK:** Low (a approach approval-tier já existe; isto é sobre defaultar shell para approval quando commitando).
6. **VALUE:** Medium.

**Robusto aqui:** O boundary check de `isPathInAllowedRoots` é correto (sem bug `/foo` vs `/fo`). A isolation do ledger (`ledger.ts:122-144`, per-repo identity, hooks disabled, gpg off) é exemplar — o bookkeeping do agente provavelmente não pode leakar ou poluir o git config/hooks do usuário. O model permission-tier (read/write/destructive) e o hard-block do plan mode com a narrow `*.md` exception (`localRun.ts:217`) são sound. Cross-repo *read* é corretamente allowed (`read_file`/`list_dir` não têm root check), matchando a expectation da dimensão.

# Crédito Explícito — O Que Está Correto e Robusto

- **Dimensão 2 é a área mais forte.** A separação `task-anchor` vs `task-checkpoint` é enforcement consistente em todo read site (`tasks.ts:147, 158, 207`); checkpoints nunca podem virar a "CURRENT task". A ghost window de search-index-lag (`tasks.ts:53-67`), o cascade sequential-batch com user-requested-task protection (`run.ts:226-244`), e a regra explicit no-fallback-to-anchor de `fetchLatestCheckpoint` (`tasks.ts:200-205`) são todos exatamente certos.
- **O hardening da Dimensão 3 é genuinamente thoughtful** — contrato reference-only em prefix+intro+summarize-instruction, re-fold idempotente tolerante do prefixo legacy, defanging de executable-fence, preservação de last-user-message no tail, e fail-safe-on-error. O único issue é o *role channel* (3.1), não o text contract.
- **O model four send-mode (Dimensão 5) é bem-designed.** `redirect` como default (cancel + keep queue + front-insert) é o default correto e a maioria dos agentes erra isto. O failed-turn no-auto-drain gate (`chatController.ts:294, 402`) e o dispatch-catch no-auto-send (`chatController.ts:347-358`) são ambos safeguards corretos contra failed turn mascarar como continuation normal.
- **Identidade de turno (Dimensão 4) é sólida** — seq monótono persistido em meta.json com reconstruction fallback do ledger (`session.ts:99-108`), orphan-recovery preservando o requested id (`session.ts:76-87`), attemptId per hop (`turnRunner.ts:245`), e o controller capturando `lastLogicalTurnId` do `turn-start` event para retry reuse (`chatController.ts:391-393`). Dedup de transport-double-delivery é sound (`controllerQueue.ts:156-167`).
- **A isolation do ledger (Dimensão 6) é exemplar** — repo git isolado per-session com sua própria identity, `core.hooksPath /dev/null`, `commit.gpgsign false` (`ledger.ts:122-144`); o bookkeeping do agente provavelmente não pode tocar o git config ou hooks do usuário. O boundary check de `isPathInAllowedRoots` (`writeRootGuard.ts:23-30`) é correto sem prefix bug.
- **Permission tiers e plan mode** (`permissionTiers.ts`, `localRun.ts:217`) são coerentes; `shell` corretamente classificado destructive; a narrow `*.md` exception do plan mode é bem-reasoned.
- **O contrato de self-demeaning authority dos reminders** (`controllerHubState.ts:81-89`, `todos.ts:254-264`) — dizendo explicitamente ao modelo que estes cedem a redirects/cancels — é a disciplina prompt-level certa; só não é suficiente por si só (daí 1.1).

O codebase mostra evidência clara de raciocínio cuidadoso sobre cada um destes hazards (os comentários são incomumente precisos sobre *por que* cada guarda existe). Os defeitos acima são na maioria casos onde um *intent* prompt-level/host-level correto é undercut por um *mechanism* gap específico (retry message duplication, abort não honrado por file tools, shell command-content não contido, summary role channel contradizendo seu texto).
